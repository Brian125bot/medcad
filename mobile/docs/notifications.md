# Dose reminders (COR-76)

Local, offline dose reminders scheduled with **expo-notifications 57**. Nothing
is sent from a server: the OS fires each reminder at its scheduled time, with
the phone locked or offline, as long as it is scheduled.

> **Device status:** the engine is tested under Node only. Every item in
> [Device acceptance checklist](#device-acceptance-checklist) is unverified
> until it is run on a physical iPhone and Android phone (same dev build as
> COR-88 / COR-91). Expo Go cannot run it; use a development build.

## How it fits together

```
screens ──save──▶ MedicationRepository ──(after commit)──▶ RepositoryChange
                                                              │
app start / foreground ─────────────────────────────▶ ReminderEngine (reconciler.ts)
                                                              │ reads meds, settings, 15 days of logs
                                                              ▼
                                                  planNotifications (planner.ts, pure)
                                                              │ desired set
                                                              ▼
                                        NotificationSchedulerPort (expo-scheduler.ts)
```

- **One hook, no screen scheduling.** `MedicationRepository.subscribe()` emits
  `medication-saved`, `medication-deleted`, `dose-changed`,
  `preference-changed` and (from `deleteVault`) `vault-deleted`, only after the
  transaction commits. Listener errors are logged and never undo the write.
  `bulkSaveMedications` emits one event per medication; the engine coalesces.
  `preference-changed` was added beyond the brief so the global settings
  reschedule too.
- **Reconcile, don't patch.** Every trigger runs the same diff: plan the next
  14 days, list what the OS has in the `cx.dose.` namespace, cancel stale or
  changed entries, schedule missing ones. Entries match on id, fire instant
  (epoch ms) and a content hash. Only one reconcile runs at a time; triggers
  during a run cause exactly one follow-up.
- **Boundaries.** `types`, `fire-time`, `planner`, `content`, `chime`,
  `ports`, `settings` and `reconciler` import no React Native / Expo and are
  covered at 100 % by Vitest. Only `expo-scheduler.ts`, `expo-clock.ts` and
  `index.ts` touch native APIs. ESLint `no-restricted-imports` and
  `tests/notification-boundary.spec.ts` stop anything outside
  `lib/notifications/` importing `expo-notifications` or the adapters.
- **Startup.** `app/_layout.tsx` starts the engine after fonts and
  `getStorageContext()` resolve, and reconciles whenever the app returns to the
  foreground. Not started on web.

## Planning rules

| Rule | Value / behaviour |
| --- | --- |
| Horizon | today … today + 14 days (inclusive), civil date keys from `lib/schedule/date-keys` |
| Which doses | active medications, `getScheduledDosesForDate` (existing daily / specific-days / interval rules), slots with reminders on, no `taken` / `skipped` log |
| Fire time | dose time − `getEffectiveLeadMinutes(slot, global default)`; crossing midnight moves to the previous date key; must be strictly after now |
| Grouping | one notification per identical fire instant (not per dose time); loudest profile wins (sound = any, vibrate = any) |
| Ids | `cx.dose.<fireDateKey>.<HHmm>`; `cx.snooze.` (COR-77) and `cx.refill.` (COR-78) are never touched |
| Budget | at most 48 `cx.dose.` entries including the sentinel; 16 more are left for COR-77 / COR-78 (iOS keeps 64 pending) |
| Sentinel | whenever any active medication has a reminder-enabled slot, one budget slot is `cx.dose.sentinel` ("Open CadenceRx to keep reminders on"). Truncated: 5 min after the last kept reminder. Not truncated: 09:00 on today + 13, but never earlier than now + 5 min. `truncated` means the budget cut dose reminders |
| Clock | domain code takes an explicit `{ todayKey, minuteOfDay }`; `expo-clock.ts` is the only caller of `civilToLocalDate` |

Planning 50 medications × 8 slots × 14 days takes ~20 ms under Node with
coverage (`notification-planner.spec.ts`).

## Content and privacy

- Default title **"Medication reminder"**, body **"2 doses due at 8:00 AM"** —
  no medication names on the lock screen.
- Names appear only if *Show medication names in notifications* is on
  (encrypted preference `notifications.showMedicationNames`, default off).
- `data` carries only `{ v: 1, kind: 'dose-group', doses: [{ d, m, s }] }`
  (date key, medication id, slot id) or `{ v: 1, kind: 'sentinel' }`.
- Tapping a reminder body (also from a cold start) opens Today. Lock-screen
  **Take**, **Snooze 15m**, and **Skip** run in the background (COR-77) without
  opening the app.

## Sound, vibration and channels

- `assets/sounds/cadencerx_chime.wav` — 1.2 s mono 16-bit PCM, 880 Hz + 1320 Hz
  with exponential decay, generated by `npx tsx scripts/generate-chime.ts`
  (deterministic; a test checks the committed file byte-for-byte). Registered
  via the `expo-notifications` config plugin `sounds` option.
- Android sound and vibration are per **channel** and fixed once created, so
  there are four: `reminders-sound-vibrate-v1`, `reminders-sound-v1`,
  `reminders-vibrate-v1`, `reminders-silent-v1`. Changing a channel's settings
  later requires a new id (`-v2`).
- iOS has no per-notification vibration switch, so the setting is hidden on
  iOS; vibration follows *Settings › Sounds & Haptics*.

## Settings

Regimen tab → bell → **Reminders** (`app/reminder-settings.tsx`):

- Global: default lead time (`notifications.defaultLeadMinutes`: at time, 5,
  10, 15, 30, 60 min) and show-names toggle.
- Per medication: sound, vibration (Android), lead time. "Default" clears the
  slots' lead times; a value writes the same lead time to every slot; slots
  that differ show **Mixed**. Alerts are stored in the encrypted medication
  payload (`alert: { sound, vibrate }`, absent = both on).
- Permission is requested when the wizard saves a medication with reminders,
  when a reminder switch is turned on, and when the settings screen opens.

## Platform notes and Expo 57 deviations from the brief

- Foreground presentation uses `shouldShowBanner` / `shouldShowList`
  (`shouldShowAlert` is deprecated in 57).
- **Exact alarms (Android 12+).** `app.json` declares `SCHEDULE_EXACT_ALARM`
  (not `USE_EXACT_ALARM`). Android does not pre-grant it to new installs on
  Android 14+. Expo 57 picks exact (`setExactAndAllowWhileIdle`) or inexact
  (`setAndAllowWhileIdle`) **when each alarm is scheduled**, and exposes no JS
  API for that state. The local Expo module `modules/exact-alarm` (Android
  only, autolinked from `modules/`) adds `canScheduleExactAlarms()` and
  `openExactAlarmSettings()` (this app's *Alarms & reminders* page via a
  `package:` URI). `expo-exact-alarm.ts` loads it with
  `requireOptionalNativeModule`, so Expo Go, iOS and web get `null` and the
  status is `unknown`.
  - Each scheduled entry records whether it was set while access was allowed
    (`exact` in the schedule metadata below). `exact = status !== 'denied'`, so
    `unknown` never causes churn. When access is granted later, the next
    reconcile (foreground) sees `exact: false` and replaces every entry once.
    Per the Android docs, revoking access stops the app and cancels its future
    exact alarms; the next launch reconciles and re-arms them.
  - When access is denied the status is `exact-alarm-denied` and the Reminders
    settings banner shows. The medication wizard also shows a one-time
    "Allow exact reminders" alert after notification permission is granted
    (encrypted preference `notifications.exactAlarmPrompted`).
  - The Kotlin module has not been compiled in CI (no Android SDK); the first
    Android development build is its compile gate.
- **Schedule metadata.** iOS reports a pending date trigger back as a relative
  time interval, so each request's `data` carries non-PHI metadata
  `sched: { at, hash, exact }` (fire epoch ms, `hashReminderContent` of the
  content without the metadata, exact-alarm flag). `listScheduled()` reads the
  fire time from an Android date trigger, otherwise from `sched.at`, and the
  hash and `exact` from the metadata, so a cold start reschedules nothing that
  is still correct. Entries scheduled by a build without metadata mismatch
  once and are replaced once.
- Reboot: Expo's boot receiver re-arms scheduled alarms on Android.
- Time-zone changes: Android alarms are absolute; the next foreground
  reconcile sees the epoch mismatch and reschedules at the new local time.
- Vault deletion cancels only `cx.dose.` entries;
  `cancelAllScheduledNotificationsAsync` is never called.

## Status reported to the UI

`useReminderStatus()` → `{ state: 'ok' | 'permission-denied' |
'exact-alarm-denied' | 'error', lastReconciledAt, scheduledCount, truncated }`.
Permission denied cancels every already scheduled `cx.dose.*` entry and
schedules nothing (`scheduledCount: 0`). `cx.snooze.*` is not part of that
cancel. Scheduler errors are logged (no PHI) and retried on the next trigger.

## Interactive actions (COR-77)

Category **`dose_reminder`** (Expo disallows `:` / `-` in category ids) is set
only on dose-group reminders and on `cx.snooze.` follow-ups. Sentinel and
window-end reminders omit `categoryIdentifier`, so they do not show Take /
Snooze / Skip. `hashReminderContent` includes the category (null when absent),
so a category change rewrites an already-scheduled entry on the next reconcile.
The category registers three actions:

| Action id | Label | Effect |
| --- | --- | --- |
| `TAKE_DOSE` | Take | `logDose(…, 'taken')` for every **pending** dose in `data.doses` (see below); inventory follows the normal repository path; idempotent re-take does not double-decrement. |
| `SNOOZE_15M` | Snooze 15m | Schedules one follow-up under `cx.snooze.<fireDateKey>.<HHmm>` (~15 minutes from the action) for **pending** doses only; cancels and **dismisses** the acted-on notification; cancels matching pending `cx.dose.` entries for those doses. Snoozes sit outside the 48-entry dose budget. |
| `SKIP_DOSE` | Skip | `logDose(…, 'skipped')` for every **pending** dose in the group; no inventory change. |

Pure `planNotificationAction` maps action id + payload → repository operations;
`executeNotificationAction` runs them through the encrypted repository and
scheduler ports. Malformed `data` is rejected; logs record **error class names
only** (no PHI).

**Pending-only actions.** Before Take, Skip, or Snooze runs, the executor loads
dose logs for the payload date range and keeps only doses with no log, on an
active medication, with a known slot. If nothing is pending, Take/Skip still
clear the notification and refresh the badge without writing. Snooze schedules
nothing when all doses are logged or already covered by a **future** `cx.snooze.`
entry (`listScheduled()` `doseKeys`). Stale snooze notifications cannot flip a
dose that was logged in-app.

**Dedupe.** Each action delivery is keyed by
`notificationId|actionIdentifier|deliveredAtMs` (delivery time from
`Notification.date`, normalized to epoch ms). A preference store
(`notifications.handledActionResponses`, TTL 7 days, max 64) plus an in-process
set ensures the background task, JS listener, and cold-start
`getLastNotificationResponse()` path execute at most once. Malformed payloads and
vault failures are not recorded. Writes to the dedupe preference do not trigger
reconcile.

**iOS unlock.** All three actions set `isAuthenticationRequired: true` on the
category (Android ignores it). The vault key stays `WHEN_UNLOCKED` in Secure
Store, so the user must unlock before Take/Snooze/Skip can read the vault. If
`logDose` fails, the notification stays visible for retry; badge refresh errors
are swallowed.

**Dismissal.** After a successful action, the executor cancels the scheduled
alarm and calls `dismissNotificationAsync` so Android removes the notification
from the shade (action buttons do not auto-cancel).

**Snooze suppression and cleanup.** While a `cx.snooze.` entry is still scheduled
(`fireAtMs` in the future), the reconciler reads each entry's `doseKeys` and the
planner skips those doses so it does not re-arm the original `cx.dose.`
reminder. Each reconcile also cancels `cx.snooze.` entries whose `doseKeys` are
all logged or refer to missing/inactive medications. Log reads widen to the
earliest snooze dose date when needed. **`vault-deleted`** cancels both
`cx.dose.` and `cx.snooze.` (never `cx.refill.`).

**Badge.** After every successful action and every reconcile, `setBadgeCount`
sets the app badge to pending doses for **today** using the same helper as the
Today tab. Zero pending clears the badge.

**Background delivery and entry.** `addNotificationResponseReceivedListener` and
the Android `expo-task-manager` task (`cadencerx-reminder-action`) both call
`dispatchNotificationResponse()` (shared dedupe). `mobile/index.ts` imports
`lib/notifications/background-task` **before** `expo-router/entry` so
`TaskManager.defineTask` runs on headless Android starts; the task is not
registered on web. Cold-start taps are processed in `startReminderEngine` before
navigation; body taps still open Today.
